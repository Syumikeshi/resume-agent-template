# 方法论 —— 简历工程的工作法

> 本文档是给「人」看的详解；给 Agent 执行的浓缩版在 [AGENTS.md](../AGENTS.md)。
> 这套方法在一个真实求职项目里打磨了 60+ 轮迭代，以下是可迁移的部分。

## 1. 为什么把写简历当工程项目

求职的产出（简历、清单、追踪表、熟悉记录）之间有**依赖关系**：简历引用档案事实，
清单引用求职约束，追踪表由清单派生，熟悉记录引用简历断言。没有工程化管理时的典型失败：

- 改了一处 GPA 口径，三份文档里还有两份是旧的
- 投了 80 家公司，没有人记得每家的状态和截止日期
- AI 对话开一次丢一次上下文，每次重头解释一遍自己是谁

解法就是下面四件事：**分层文档、唯一真相源、派生流水线、断言出处对照**。

## 2. 四层文档模型

信息按**变更频率**分层，改东西时只动对应层：

| 层 | 文件 | 性质 | 何时写 |
|---|---|---|---|
| 1. 入口 | `README.md` | 项目是什么、目录怎么走 | 结构变化时 |
| 2. 快照 ★ | `memory/MEMORY.md` | 当前状态（**唯一真相源**），覆盖更新 | 状态变化时 |
| 3. 流水·索引 | `memory/CHANGELOG.md` | 一行一轮的轮次索引 | 每轮结束 |
| 4. 流水·细节 | `memory/session-log.md` + `memory/YYYY-MM-DD.md` | 每轮五块结构 / 当日速记，**只追加** | 每轮结束 |

三条纪律：

1. **快照可覆盖，流水只能追加。**「现在是什么样」与「怎么变成这样的」分开存。
2. **同一事实只在一处定义。** 权威数字（GPA、薪资底线、毕业时间、公司截止日）只在
   MEMORY.md 的「权威数字」节定义；其他文件（简历 tex、清单、熟悉记录）引用它，不复制它。
3. **改完交付物回写源。** 每类交付物都有「源」：PDF ← tex，xlsx ← 清单 md，docx ← md 草稿。
   在产物上做的可持久修改必须回到源，否则下次重建就退回旧内容。

**换工具 / 换 Agent / 开新会话的最小交接集：MEMORY.md 一份。**

## 3. 轮次工作法（和 AI 协作的节奏）

一轮 = 一次有明确诉求的对话。结束时做四件事：

1. **追加会话日志**，固定五块：本轮诉求 / 结论 / 改动文件 / 待用户决策 / 下一步。
   「待用户决策」单独列出，避免悬而未决的问题沉底。
2. **更新 MEMORY.md** 的待办与状态（覆盖式）。
3. **提交 git**：`第 N 轮：<主题>`，与 CHANGELOG 索引对齐。
4. **里程碑打 tag**（简历定稿 / 首批投递完成 / 拿到 offer），之后 `git diff <tag> --stat`
   可以随时回看某阶段以来发生了什么。

## 4. QA 审计方法论

### 4.1 简历五项体检（每次改版必跑）

1. **页数**：逐份查（中文版比英文版占版面，不能只查一个语言版本）
2. **Overfull hbox**：`grep -c "Overfull" *.log`，任何越界都可能在 ATS 解析时出问题
3. **文本层**：`pdftotext <file> -` 确认文字（尤其数字）能提取——有的字体组合会让
   PDF 视觉正常但文本层为空
4. **元数据**：`pdfinfo` 查 Author / Title / Keywords 无乱码、无旧内容
5. **黑白脱色**：黑白版用取色器确认强调色真的变成纯黑（#000000），不是「看起来灰」

### 4.2 页边距测量（判断还能不能塞一行）

把 PDF 转成位图（`pdftoppm -png -r 150`），扫描非白像素的上下边界，
与 geometry 设定的页边距对比——量化「还剩多少空间」，而不是凭感觉。

### 4.3 交付物依赖图（修正的传播）

事实 → 简历 tex → PDF → 清单备注 → 熟悉记录，是一条引用链。**确认一处事实性修正后，
沿依赖图排查所有下游交付物**——修正不会自动传播，忘一处就是面试现场的定时炸弹。
建议在 MEMORY.md 维护一张「关键事实 ↔ 引用它的交付物」对照（可由断言出处对照表直接得到）。

### 4.4 简历超页时的删减优先级

经验顺序（从先删到最后删）：

1. 与目标方向无关的经历整条
2. 描述性副词与重复的技能罗列
3. 早期教育的课程明细（保留学位 + GPA + 奖项）
4. 合并同类 bullet（两条说一件事的并成一条）
5. **最后才动格式**（字号 / 行距 / 边距）——ATS 可读性优先于塞更多信息

## 5. 投递清单与追踪表

- **梯队制**：第一梯队（最想去）/ 第二梯队 / 第三梯队 / 需确认（信息不足）/ 建议放弃（明确排除）。
  「建议放弃」也留着——排除的决策与理由同样是资产。
- **清单是唯一真相源**：markdown 写决策，脚本生成 xlsx 追踪执行。改公司/梯队/薪资 → 改清单重跑；
  xlsx 里只填过程数据（投递日期、进展）。
- **追踪表增量更新**：`build.py` 默认按「表名+企业名」沿用旧表的投递日期/进展，
  现场记录整表保留；`--rebuild` 才全量重做。派生物重建不等于过程数据丢失——
  「唯一真相源」管结构性内容，「增量」管用户手填的过程数据。
- **薪资要带核实状态**：「18-25K（待核实）」优于一个干净但没验证的数字。

## 6. 文档类交付物的流水线约定（docx 等）

如果产出 Word 文档（作品集、报告等），保持三段式结构与回写纪律：

```
stage1/final_draft.md   ← 源（markdown）
stage2/*.html           ← 中间（排版载体）
stage3/*.docx           ← 产物
```

**在 docx 上做的修改必须回写 stage1 的 md**，否则下次从源重新生成会退回旧内容。
产物目录带一个索引 README：request_id → 交付物名 → 各阶段路径。

## 7. 隐私与公开

- 本模板仓库**不含任何真实个人信息**；你的个人数据只应出现在 `input/`、`memory/` 与你的构建产物里
- 把你自己的求职仓库公开前，检查：input/ 素材、MEMORY.md 档案节、会话日志（对话里可能提到电话邮箱）、
  git 历史（提交过的东西永远在历史里）
